Request to Grafana

How one API call turns into an API log, server logs and a trace, which component carries each one, which file sets it up, and how to pull API or server logs out separately in Grafana.

Scope: the local lab (bootstrap/envs/local, apps/local, observability/local). dev, staging and prod run the same pipeline from the same files with production sizing: two collector tiers with 100%, 50% and 10% of healthy, fast traces kept, Alloy as two clustered replicas, Loki and Tempo on S3, Prometheus and Alertmanager in HA, Grafana behind OIDC. Metrics aren't drawn here; Prometheus scrapes each service's /actuator/prometheus through its ServiceMonitor and the collector's span metrics.

The path

request logs traces trace context only, no span data

Edge, API or server logs?

One request leaves up to three kinds of line, from the outside in. There's no Grafana setting that splits them: what differs is who wrote the line, and Alloy records that as the log_type label. All three carry the request's trace_id.

Edge log log_type="edge"

One line per request from the ingress (Traefik in the lab), as the client saw it: status, total time including the hop to the pod, client address. It also records requests that never reached a service, such as routing errors or a pod that was down. In the cloud the ALB writes this log to S3 instead.

Use it to see what users actually got.

API log log_type="api"

One line per HTTP request inside the service, written by RequestLoggingFilter after the response is sent. Logger access.<service>.http, message http_request, with OpenTelemetry field names: method, path, route template, status, duration, and the request payload where the environment turns it on (lab and dev: every request; staging and prod: failed requests only), with secret fields masked. Response bodies are never logged; health checks aren't logged at all.

Use it to see what was called, with what, how long it took and what status came back.

Server log log_type="server"

Everything else the service writes: startup, business and audit events (audit.<service>.*), auth failures, and unhandled_exception with its stack trace.

Use it to see why a request behaved the way it did.

  • Dashboard

    Dashboards → Microservices → API calls (one readable line per request, payload included where logged) and Edge requests. The Log type dropdown at the top (All, api or server) drives the Application Logs panel.

  • Explore

    Explore → datasource Loki → Label browser → log_type → edge, api or server → Show logs.

  • Query

    {namespace="development", log_type="api"}
    or log_type="server", or {namespace="traefik", log_type="edge"}. The query cards below add parsing and formatting.

To follow one request from its edge or API line to its server logs and trace, click trace_id on the log line.

<timestamp>
@timestamp
<pattern>
service from spring.application.name, environment from DEPLOYMENT_ENVIRONMENT (set per overlay, same value as the traces' deployment.environment)
<mdc/>
trace_id, span_id, trace_flags, put there by the Java agent while the request's span is open
<arguments/>
every kv(...) passed to the logger becomes a top-level field
<stackTrace>
the whole stack trace as one escaped string in exception, so it stays one line

The server line is written first because RequestLoggingFilter logs in its finally block, after the controller returns. Both lines carry the same span_id: the agent's HTTP server span covers the whole filter chain.

How it gets deployed

The podman flow, in the order the scripts run it. ArgoCD is installed for its UI but doesn't sync; sync-local-stack.rb installs the charts directly from the same Application files. With Docker, start-lab.sh applies root-app-local instead and ArgoCD does steps 4 and 5.

  1. scripts/start-lab-podman.sh

    Builds frontend, order-service and user-service from ../app. Each backend Dockerfile downloads the OTel Java agent 2.13.3 (checksum-pinned) and starts Java with -javaagent.

  2. kind create cluster · kind load image-archive

    Creates dev-lab from kind-config.yaml: one control plane, two workers, host ports 80 and 443. Loads the three images.

  3. start-lab.sh via with-podman.sh

    Adds the gp3 StorageClass, ArgoCD v2.13.3, Traefik v3 as the ingress controller (removing an old ingress-nginx first), and the app-secrets Secret from apps/local/app-secrets.env.

  4. scripts/sync-local-stack.rb

    Turns ArgoCD auto-sync off if it\'s on, then runs helm upgrade --install for each add-on in addons/applications with its values from addons/values/{common,local}: kube-prometheus-stack, metrics-server, loki, tempo, otel-collector, otel-collector-sampler, alloy.

  5. kubectl apply -k apps/local · observability/local

    The services with their OTEL_* and DEPLOYMENT_ENVIRONMENT settings, then the alert rules, SLO rules, dashboards and the /otlp Ingress.

Before a cloud environment goes live

The lab runs as committed. dev, staging and prod still need values only their AWS account has; until then the pieces below won't start or won't notify.

  1. –

    Storage logstracesmetrics

    Apply the tf repo's 01-infra and 02-services layers first. They create the EBS CSI driver addon, the Loki and Tempo S3 buckets, and the IRSA-annotated loki and tempo ServiceAccounts. platform/storage adds the gp3 (default) and gp3-retain StorageClasses. The bucket names in addons/values/<env>/{loki,tempo}.yaml assume account 602367507570; change them if an environment lives in another account.

  2. –

    Secrets in AWS Secrets Manager alerting · Grafana

    microservices/<env>/alerting (slack_webhook_url, pagerduty_routing_key, heartbeat_url), /grafana (admin_user, admin_password) and /grafana-oauth (client_id, client_secret, auth_url, token_url, api_url, root_url).

  3. –

    Hosts, DNS and the shared ALB ingress

    Grafana's host per environment (addons/values/<env>/kube-prometheus-stack.yaml) with an ACM certificate. Joining the microservices IngressGroup gives an existing environment a new app ALB DNS name once. Put a WAF rate limit on /otlp before relying on it in prod.

  4. –

    Optional: long-term metrics metrics

    Remote write to Amazon Managed Prometheus is documented in addons/values/cloud/kube-prometheus-stack.yaml and left off until a workspace and IRSA role exist.

Alerts and SLOs

Rules live in observability/base, are deployed to every environment, and are unit-tested with promtool. Every alert links to its section of docs/runbooks.md.

SLOs
99.5% of requests without a 5xx and 99% within 500ms, per service, over 30 days; multi-window burn-rate alerts page at 14.4x/6x and open a ticket at 3x/1x (Google SRE workbook).
Service
ServiceDown, ServiceMetricsMissing; pod and node health come from kube-prometheus-stack's default rules.
Pipeline
Alloy missing, stalled or dropping lines; Loki rejecting or failing pushes; the collector losing spans, its queue filling, the sampler overloaded or unreachable; Tempo discarding spans.
Routing
Cloud: critical → PagerDuty and Slack, warning → Slack, Watchdog → a dead man's switch heartbeat. Lab: shown in Grafana and the Alertmanager UI only.

Query it

Open Grafana with kubectl port-forward svc/kube-prometheus-stack-grafana 3000:80 -n monitoring, then Explore. Swap the namespace for other environments.

API logs

Loki 
{namespace="development", log_type="api"}
  | json
  | http_response_status_code >= 400
  | line_format "{{.http_request_method}} {{.http_route}} {{.http_response_status_code}} {{.duration_ms}}ms {{.http_request_body}}"

Failed requests with their payload. Drop the status filter for every request. | json turns fields into filters, with dots replaced by underscores.

Edge requests

Loki 
{namespace="traefik", log_type="edge"}
  | json
  | KubernetesIngressNamespace="development"
  | line_format "{{.RequestMethod}} {{.RequestPath}} {{.DownstreamStatus}} {{div .Duration 1000000}}ms"

What clients got at the entrance (lab: Traefik). Duration is in nanoseconds.

Server logs

Loki 
{namespace="development", log_type="server"}

Startup, business and audit events. Add | json | logger =~ `audit\..*` for audit only.

Errors with stack traces

Loki 
{namespace="development", log_type="server"}
  | json
  | level = "ERROR"

unhandled_exception lines carry the full stack trace in the exception field.

One request across logs

Loki 
{log_type=~".+"} |= "4bf92f3577b34da6a3ce929d0e0e4736"

Paste a trace ID from Tempo, or click Logs for this span there, which runs the same query. trace_id is inside the line, not a label, so it's a line filter.

Failed requests

Tempo · TraceQL 
{ resource.service.name = "user-service" && span.http.response.status_code >= 500 }

Drop the second condition to list every user-service trace.

Is the collector receiving?

Prometheus · PromQL 
sum(rate({__name__=~"otelcol_receiver_accepted_spans(_total)?"}[5m]))

Spans accepted per second. The regex matches the metric with or without the _total suffix, which changed across collector versions.
