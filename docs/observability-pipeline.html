Request to Grafana

How one API call turns into an API log, server logs and a trace, which component carries each one, which file sets it up, and how to pull API or server logs out separately in Grafana.

Scope: the local lab (bootstrap/envs/local and apps/local). dev, staging and prod run the same pipeline with 100%, 50% and 10% trace sampling, Alloy as two clustered replicas, and Loki on an S3 bucket that still has placeholder names. Metrics aren't drawn here; Prometheus scrapes each service's /actuator/prometheus through its ServiceMonitor.

The path

request logs traces trace context only, no span data known limit, see below

API logs or server logs?

Both are JSON lines from the same Spring Boot process, so there's no Grafana setting that splits them. What differs is who wrote the line, and Alloy records that as the log_type label.

API log log_type="api"

One line per HTTP request, written by RequestLoggingFilter after the response is sent. Logger access.<service>.http, message http_request, with method, path, status and duration in milliseconds.

Use it to see what was called, how long it took and what status came back.

Server log log_type="server"

Everything else the service writes: startup, business and audit events (audit.<service>.*), auth failures, and unhandled_exception with its stack trace.

Use it to see why a request behaved the way it did.

  • Dashboard

    Dashboards → Local Microservices → Log type dropdown at the top: All, api or server. The Application Logs panel follows it.

  • Explore

    Explore → datasource Loki → Label browser → log_type → api or server → Show logs.

  • Query

    {namespace="development", log_type="api"}
    or log_type="server". The query cards below add parsing and formatting.

Lines shipped before the label existed don't have log_type. For those, filter on the JSON field instead: | json | logger=~"access\\..*" for API logs, !~ for server logs. To follow one request from its API log to its server logs and trace, click trace_id on the log line.

<timestamp>
@timestamp
<pattern>
service from spring.application.name, environment from DEPLOYMENT_ENVIRONMENT (set per overlay, same value as the traces' deployment.environment)
<mdc/>
trace_id, span_id, trace_flags, put there by the Java agent while the request's span is open
<arguments/>
every kv(...) passed to the logger becomes a top-level field
<stackTrace>
the whole stack trace as one escaped string in exception, so it stays one line

The server line is written first because RequestLoggingFilter logs in its finally block, after the controller returns. Both lines carry the same span_id: the agent's HTTP server span covers the whole filter chain.

How it gets deployed

The podman flow, in the order the scripts run it. ArgoCD is installed for its UI but doesn't sync; sync-local-stack.rb installs the charts directly from the same Application files. With Docker, start-lab.sh applies root-app-local instead and ArgoCD does steps 4 and 5.

  1. scripts/start-lab-podman.sh

    Builds frontend, order-service and user-service from ../app. Each backend Dockerfile downloads the OTel Java agent 2.13.3 (checksum-pinned) and starts Java with -javaagent.

  2. kind create cluster · kind load image-archive

    Creates dev-lab from kind-config.yaml: one control plane, two workers, host ports 80 and 443. Loads the three images.

  3. start-lab.sh via with-podman.sh

    Adds the gp3 StorageClass, ArgoCD, ingress-nginx v1.12.1 with its OTel exporter pointed at the collector, and the app-secrets Secret from apps/local/app-secrets.env.

  4. scripts/sync-local-stack.rb

    Turns ArgoCD auto-sync off if it's on, then runs helm upgrade --install with the charts in addons/applications and the values in addons/values: kube-prometheus-stack, metrics-server, loki, tempo, otel-collector, alloy.

  5. kubectl apply -k apps/local

    Adds the OTEL_* and DEPLOYMENT_ENVIRONMENT env vars to both services, the ingress OTel annotations, the Grafana dashboard ConfigMap and the PrometheusRule.

Known limits

Number 1 matches the marker on the diagram.

  1. 1

    The browser span never reaches Tempo traces

    traceFetch() makes up a parent span ID and only writes it to the browser console. The ingress trusts that header, so its span hangs off a parent Tempo never receives and the trace view shows a missing root. The upside is that the trace ID in the browser console matches the backend logs and Tempo.

    To close it: replace traceFetch() with the OpenTelemetry browser SDK and export to the collector through the ingress (needs an OTLP/HTTP route and CORS on the receiver).

  2. –

    Loki in dev, staging and prod needs real S3 settings logs

    addons/values/cloud/loki.yaml still has placeholder bucket names and region, and expects a pre-created loki ServiceAccount with an IRSA role. Until both exist, Loki won't start in those environments.

Query it

Open Grafana with kubectl port-forward svc/kube-prometheus-stack-grafana 3000:80 -n monitoring, then Explore. Swap the namespace for other environments.

API logs

Loki 
{namespace="development", log_type="api"}
  | json
  | http_path !~ `.*/actuator/.*`
  | line_format "{{.http_method}} {{.http_path}} {{.http_status}} {{.http_duration_ms}}ms"

One line per request. The actuator filter hides the readiness probe every 5s and the liveness probe every 10s.

Server logs

Loki 
{namespace="development", log_type="server"}

Startup, business and audit events. Add | json | logger =~ `audit\..*` for audit only.

Errors with stack traces

Loki 
{namespace="development", log_type="server"}
  | json
  | level = "ERROR"

unhandled_exception lines carry the full stack trace in the exception field.

One request across logs

Loki 
{log_type=~".+"} |= "4bf92f3577b34da6a3ce929d0e0e4736"

Paste a trace ID from Tempo, or click Logs for this span there, which runs the same query. trace_id is inside the line, not a label, so it's a line filter.

Failed requests

Tempo · TraceQL 
{ resource.service.name = "user-service" && span.http.response.status_code >= 500 }

Drop the second condition to list every user-service trace.

Is the collector receiving?

Prometheus · PromQL 
sum(rate({__name__=~"otelcol_receiver_accepted_spans(_total)?"}[5m]))

Spans accepted per second. The regex matches the metric with or without the _total suffix, which changed across collector versions.
